The problem

Staff kept records by hand, across tools that never talked.

NYU Client Service staff processed maintenance requests by hand — a CSV here, a legacy screen there — and jumped between systems to find any request’s history.

A representative request — Type “Campus Cash,” Problem Code B801, “Campus cash — laundry refund” — had no single accurate record to communicate from. Neither did any other request.

B801 · CSV file → B801 · Legacy system → B801 · Invoice screen

The same request, re-typed into each tool. Nothing carried over.

“As a Client Service Staff at NYU, I want to have an accurate maintenance record so that we can communicate more effectively with departments and clients.” User story from process work

The insight

A request is a workflow, not a row of data.

I mapped how a request travels — submitter, Client Service Center, maintenance department — and found that most requests are multi-step and cross departments.

That changed the brief from “replace the CSV with a form” to “represent a request’s full lifecycle in one place.”

SubmittersStudent, faculty, campus staff raise a request
→
Client Service CenterReceives, reviews, approves — the project’s focus
→
MaintenanceOperators and supervisors perform the work order

The solution

Four shipped decisions.

We stated the bet before we built: with one record, staff communicate confidently, process faster, and train new employees more easily.

01Unify the platform

I replaced the CSV files and multiple platforms with one work-order platform, so there was nothing left to switch between.

02Keep the form continuous

I weighed overload against scannability and chose a continuous form over a paginated one: a multi-department request stays visible in one pass.

03Keep the action reachable

I weighed button visibility against minimizing distraction and kept the floating action button — the primary action stays in reach while staff review dense request details.

04Split the review

I ran two pre-launch loops: Client Service and maintenance staff signed off on workflow; engineering walked specs and edge cases per request type.

Outcome

We decided what to measure before we shipped. Then it reported back.

We set the measurement plan in the deck before launch and instrumented all three metrics on day one. The first to report back was average work-request turnaround.

~33% lower average work-request turnaround First month post-launch · our own analytics

Honest denominator: the ~33% comes from our own first-month post-launch analytics, not the deck. It’s early and directional — but the plan behind it was set before we shipped.

Post-launch · What I’d measure next

Pre-launch review flagged the next scope: search, and grouping multiple work orders. Next I’d measure the overload-versus-scannability tradeoff directly, and track remaining email-heavy overhead.

The open question I still carry is how much of a service problem belongs in the digital tool, and how much in the physical space around it.

Problem

No accurate, unified record to communicate from.

NYU Client Service staff processed campus maintenance requests by hand across disconnected tools. Data entry was manual and slow. Staff jumped between systems just to find a request’s history or keep records current.

A representative request: Request Type “Campus Cash,” Problem Code B801, “Campus cash — laundry refund.” Every request had the same underlying problem: no single accurate record to communicate from.

Many maintenance requests are multi-step and span multiple departments, so any fix had to represent a workflow rather than a static record.

“As a Client Service Staff at NYU, I want to have an accurate maintenance record so that we can communicate more effectively with departments and clients.”

Process

The record had to hold a workflow, not just data.

Early process work mapped how a request traveled from the person submitting it, through the Client Service Center, to the maintenance department, an information-architecture exercise framed as “How might we help with facility request management?” That mapping surfaced the multi-step, multi-department constraint.

It reframed the project from “replace the CSV with a form” to “represent the full lifecycle of a request in one place”: the platform had to carry the whole workflow.

If staff work from one unified record instead of many disconnected tools, they will communicate more confidently, process requests faster, and train new employees more easily.

Solution

Four shipped decisions.

  • One unified work-order platform. Replaced CSV files and multiple platforms outright, which closed the software-switching problem at the source.

  • Two separate pre-launch review loops, not one. High-fidelity prototypes went to Client Service Center staff and the maintenance department for sign-off on workflow and content, and separately to engineering for a walkthrough of specs and edge cases per request type. (The engineering loop also flagged keeping micro-interactions consistent across platforms, captured as follow-up work.)
Impact

Average turnaround fell about a third in the first month.

We instrumented three metrics at launch. The first to report back: average work-request turnaround time dropped roughly 33% over the first month post-launch.

That figure is from our own post-launch analytics, tracked over the first month and revisited in follow-ups as we looked to improve the service design: an early, directional result, not a long-run study. It isn’t in the original deck; the deck set the measurement plan, and this is what that plan returned:

“Post-launch, we will track both work request processing time, student employee training time, and communication time between client and Client Service Staff.”

That number exists because we decided what to measure before we shipped.

Learnings

What I would measure next.

  • Measure the tradeoff directly. Compare staff accuracy and task time to balance visual clutter against information complexity.
  • Track email-heavy tasks. Find where the workflow still creates communication overhead.
  • Design for upstream and downstream users differently within the same request workflow.
  • Pre-launch review flagged future scope: search functionality, and grouping multiple work orders.

The open question I still carry: how much of a service problem should be solved in the digital tool versus in the physical space around it.
