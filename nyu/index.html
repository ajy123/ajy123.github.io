Problem

No accurate, unified record to communicate from.

NYU Client Service staff processed campus maintenance requests by hand across disconnected tools. Data entry was manual and slow. Staff jumped between systems just to find a request’s history or keep records current.

A representative request: Request Type “Campus Cash,” Problem Code B801, “Campus cash — laundry refund.” Every request had the same underlying problem: no single accurate record to communicate from.

Many maintenance requests are multi-step and span multiple departments, so any fix had to represent a workflow rather than a static record.

“As a Client Service Staff at NYU, I want to have an accurate maintenance record so that we can communicate more effectively with departments and clients.”

Process

The record had to hold a workflow, not just data.

Early process work mapped how a request traveled from the person submitting it, through the Client Service Center, to the maintenance department, an information-architecture exercise framed as “How might we help with facility request management?” That mapping surfaced the multi-step, multi-department constraint.

It reframed the project from “replace the CSV with a form” to “represent the full lifecycle of a request in one place”: the platform had to carry the whole workflow.

If staff work from one unified record instead of many disconnected tools, they will communicate more confidently, process requests faster, and train new employees more easily.

Solution

Four shipped decisions.

  • One unified work-order platform. Replaced CSV files and multiple platforms outright, which closed the software-switching problem at the source.
Considered

A single continuous form view over a paginated one.
Because
One continuous view keeps a multi-department request visible in a single pass.

Kept the floating action button.
Because
The primary action needed to stay reachable while staff reviewed dense request details.
  • Two separate pre-launch review loops, not one. High-fidelity prototypes went to Client Service Center staff and the maintenance department for sign-off on workflow and content, and separately to engineering for a walkthrough of specs and edge cases per request type. Splitting the review matched sign-off criteria to the right audience: workflow accuracy from ops staff, technical completeness from engineering. (The engineering loop also flagged keeping micro-interactions consistent across platforms, captured as follow-up work.)
Impact

Average turnaround fell about a third in the first month.

We instrumented three metrics at launch. The first to report back: average work-request turnaround time dropped roughly 33% over the first month post-launch.

That figure is from our own post-launch analytics, tracked over the first month and revisited in follow-ups as we looked to improve the service design: an early, directional result, not a long-run study. It isn’t in the original deck; the deck set the measurement plan, and this is what that plan returned:

“Post-launch, we will track both work request processing time, student employee training time, and communication time between client and Client Service Staff.”

That number exists because we decided what to measure before we shipped.

Learnings

What I would measure next.

  • Measure the tradeoff directly. Compare staff accuracy and task time to balance visual clutter against information complexity.
  • Track email-heavy tasks. Find where the workflow still creates communication overhead.
  • Design for upstream and downstream users differently within the same request workflow.
  • Pre-launch review flagged future scope: search functionality, and grouping multiple work orders.

The open question I still carry: how much of a service problem should be solved in the digital tool versus in the physical space around it.
